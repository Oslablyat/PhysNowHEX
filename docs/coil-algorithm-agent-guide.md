## С чего начать

1. Прочитай корневой [AGENTS.md](../AGENTS.md) и этот файл перед изменением подбора.
2. Уточни по запросу владельца, меняется ли ограничение, целевая функция, порядок
   поиска, тепловая методика или только интерфейс. Это разные части программы.
3. Работай с **основным сайтом**: `index.html`, `app.js`, `assets/coil-project-*`.
   Экспериментальную страницу сейчас не дорабатываем без отдельной команды.
4. Проверь фактическую реализацию названных ниже функций. При расхождении
   актуальная команда владельца и код важнее старого отчёта. Не выдавай архивные
   результаты за проверку новой версии.
5. После изменения поведения обнови этот файл и соответствующие тесты.

Сейчас основной решатель имеет идентификатор `re-stock-single-re-free-v12`.
К нему уже добавлены шесть целевых функций и выбор подходящих конструкций из

## Последовательность основного расчёта

```text
Ввод / смена листа / выбор цели
  ↓
getState → withDesignDimensions → coilProjectState → coilProjectKey
  ↓ новый ключ: отменить старый запрос, убрать прежнюю таблицу
Worker: CoolProp → balance → source
  ↓ баланс отдельно возвращается в интерфейс
tubeCounts → families → shortlist
  ↓
Обычный режим: партии проверок, уточнение, резервы N, улучшение
Один змеевик: отдельная ветка N=1 внутри select
  ↓ каждый кандидат: verify → исходный Teplo.calculate → meets
  ↓
Все принятые геометрии → приватный кэш Worker
Лучший по цели → rows[balanced]
Сводки полных расчётов → calculations
  ↓
Таблица показывает только status=accepted
Автоматическая загрузка либо сохранение выбранной/ручной геометрии
```

### 1. Задание и свойства

`balance(state, props)` поддерживает воду в обоих контурах и противоток.
Горячая среда течёт внутри змеевиков, холодная — в межтрубном пространстве.
Один неизвестный выбирается среди четырёх температур и двух расходов.

- Свойства: CoolProp 8.0.0 WASM в Worker.
- Масса объёмного расхода определяется по плотности на входе.
- Теплоёмкости для баланса — при средних температурах задания.
- Получаются `q` в кВт, `requiredUA` в Вт/К, расходы в кг/с и температурный напор.
- Запас UA для змеевиков сейчас принудительно **0 %**, включая старые листы.
- Предварительная оценка UA позднее служит только для порядка поиска.

Формулы и источники подробно описаны в [teplo-project.md](teplo-project.md),
[teplo-validation.md](teplo-validation.md), [исходной методике](../assets/teplo-methodology.md).

### 2. Количество параллельных трубок

`tubeCounts` использует вязкость при средней температуре трубного потока:

```text
C = 4ṁ / (π di μ)       di — в метрах
Nmin = ceil(C / 20000)
Nmax = floor(C / 15000), с учётом общего предела 500
```

Обычно выбирается допустимое целое N, ближайшее к Re≈17500. Для цели
`tube-count` стартовое N берётся с нижней границы допустимого интервала.
`inlineReserveCounts` формирует геометрически совместимые резервы: соседние N,
границы и кратные числу рядов. Вместимость и возможность изготовимой общей
высоты проверяются до выделения полного теплового слота.

**Предварительный Re не является финальной приёмкой.** После Teplo Re каждой
трубки в обычном режиме должен попасть в 15000…20000.

При `single-coil=true` сразу N=1: предварительный и итоговый трубный Re не
ограничивает проектный подбор, но исходные предупреждения Teplo сохраняются.

### 3. Геометрические семейства и каталог

`families`, `compactGeometry`, `unrestrictedLayout`, `buildGeometry`:

- Труба по умолчанию 14×2,5 мм; при `refine-tubes=true` используется заданная.
- 1–8 концентрических рядов, не более 64 трубок в ряду, до 500 всего.
- N делится на число рядов; в каждом ряду одинаковое число заходов k.
- Радиусы от центра наружу. Первый радиус начинается на целой сетке, строго
  выше 3di и с местом для вытеснителя; дальше сетка радиуса 5 мм.
- Для каждого ряда обязательно **3 < R/di < 12**.
- Радиальные чистые зазоры в основном алгоритме **3 мм**.
- Вертикальное межосевое a=P/k: 1,1do…2do. Чистый зазор s=a−do — целое число
  миллиметров, ceil(0,1do)…floor(do). Для Ø14: s=2…14 мм.
- P=k(do+s), общее целое число витков n≤1000, рабочая высота H=nP+do.
- Число витков, P, фаза, направление и рабочая высота у рядов общие;
  offset=0, phase=0, direction=right. Ряды нельзя независимо укорачивать.
- Хордовая вместимость, нормальное расстояние наклонных винтовых линий и
  отсутствие пересечений проверяются отдельно от вертикального зазора.

**Одинаковый угол наклона навивки сейчас не задан.** Одинаковый P при разных
радиусах означает разные углы. Владелец уточнял термин, но не давал команды
ввести это ограничение. Не подменяй общий шаг одинаковым углом автоматически:
это затронет P, целые витки, общую высоту и коридорность.

Если `refine-dimensions=false`, приложение передаёт верхние границы поиска
H=10000 мм, D=3000 мм. При true используются введённые пределы. Размеры не
являются требованием заполнить весь доступный габарит. Допустимые границы
решателя: H 200…10000 мм, D 200…3000 мм.

Стенка корпуса предварительная: ceil[(pc−0,101325)D/(2×130)+0,2] мм.
Это не полный расчёт прочности. Стенка вытеснителя 2 мм.

### 4. Заготовки — независимая настройка

`stockLengthsEnabled` возвращает true и для старого листа без поля.
`single-coil` **не выключает** учёт заготовок.

При `stock-lengths=true` полная трубка каждого ряда:

```text
Lполная = Lнавивки + два пространственных отвода + два прямых конца
0,8 Lзаготовки ≤ Lполная < Lзаготовки
Lзаготовки ∈ {1000, 3000, 6000} мм
```

Отвод по оси 2do, прямой конец max(40,2do) мм. Для приёмки берётся
`CoilManufacturing.measure`; быстрая оценка длины не заменяет численный интеграл.
При выключении stock снимаются ограничения заготовки и остатка, но полная
длина продолжает измеряться, в том числе для целевой функции и таблицы.
Тепловая площадь Teplo учитывает навивку, без отводов и концов, по среднему
диаметру трубки. Не заменяй её наружной площадью 3D-модели.

### 5. Предварительный порядок и полные проверки

`screeningModel` оценивает UA по геометрии и свойствам при температурах задания.
`shortlist` формирует дискретные геометрии по целым зазорам и целым виткам.
Глобального прохода H по миллиметрам нет.

Обычная ветка `select`, все числа ниже — верхние лимиты этапов:

| Этап | Полных проверок | Особенность |
|---|---:|---|
| initial | 20 | Первое основное N |
| refinement | 24 | Перерасстановка очереди по измеренному UA |
| catalogue | 60 | Продолжение каталога |
| refinement | 24 | Уточнение |
| fallback | 24 + уточнение до 16 | Максимум четыре изготовимых резервных N |
| improvement / catalogue | Оставшийся бюджет за вычетом резерва 16 | Продолжение улучшения |
| refinement | До 16 | Финальное уточнение |
| diagnosis | До 24 оставшихся | Только если нет результата и можно расширить габариты |

Сумма этих лимитов **не** является допустимым числом вызовов: общий
`construction.maxEvaluations=200` обязателен для всех этапов и N, включая ошибки
и diagnosis. `seen` исключает повтор полного расчёта той же `geometryInput`.
Первый принятый вариант не завершает поиск и не теряется при последующих отказах.

Для цели length резервы N включаются при отсутствии результата. Для остальных
целей — также при уже найденном варианте. Невместимые или неизготовимые N не
должны занимать резервные тепловые слоты.

`calibration` меняет только оценочный порядок кандидатов. Уточнение работает
с существующими дискретными компоновками, до восьми семейств за итерацию.

Ветка одного змеевика внутри `select` отдельная: N=1, каталог целых витков и
зазоров, оценочный диапазон UA 0,85…1,15 задания, затем направленные полные
проверки с тем же общим бюджетом и точной проверкой заготовки до Teplo.

Это ограниченный эвристический поиск. Если результата нет, нельзя утверждать,
что физически подходящей конструкции не существует. Превышение габарита
объясняется подтверждённым `dimensionWitness`, а не оценкой UA. Диагностический
вариант вне исходного габарита нельзя принимать, показывать подходящим или
помещать в кэш доступных для выбора конструкций.

### 6. Приёмка — не смешивать с ранжированием

Внутренний `verify` вызывает исходный `Teplo.calculate`. Затем используются
`applicability`, `dutyAgreement`, `meets`, ограничения изготовимости и геометрии.

- Qконструкции ∈ [Qзадания, 1,01 Qзадания] с численными допусками кода.
- UA не ниже требуемого; запас сейчас 0 %.
- Горячий выход в диапазоне [Tho−0,01(Thi−Tho), Tho],
  с численным допуском 0,01 °C на обеих границах.
- Холодный выход в диапазоне [Tco, Tco+0,01(Tco−Tci)],
  с численным допуском 0,01 °C на обеих границах.
- Исходные критерии применимости Teplo, ограничения радиусов, геометрии и Re.
- В single-coil разрешено только оговорённое исключение по трубному Re.
  Raw `thermal.valid` и исходные `tube_checks` не переписываются. При нарушении
  этих критериев остаётся предупреждение о неподтверждённой применимости.

Не ослабляй допуск мощности или применимости, чтобы новая целевая функция
«нашла» больше аппаратов. В исходной методике нет Δp: не добавляй вымышленные
гидравлические результаты или постоянный K.

## Шесть целевых функций

Определения: `objectives`, `objectiveFor`, `objectiveValue`, `fullTubeMetres`,
`compare` в основном решателе. Сохранённое поле — `design-objective`.

| ID | Что минимизируется |
|---|---|
| length | Рабочая длина корпуса H; цель по умолчанию |
| tube-length | Σ(countᵢ × Lполная,ᵢ), метры всех трубок с отводами и концами |
| tube-count | Общее N параллельных трубок |
| rows | Число концентрических рядов |
| volume | πDнаруж²H/4, м³; без выступающих выводов |
| diameter | Наружный диаметр корпуса |

При равенстве основной метрики применяются H, D, вертикальный зазор, отходы,
N. Это лексикографическое сравнение, не скрытая взвешенная стоимость.
Для неизвестного/отсутствующего ID применяется length.

Цель влияет **и на очередь, и на выбор лучшего полностью принятого варианта**.
Для целей кроме length используются группы близости оценочного UA с шагом
логарифмической ошибки 0,03; внутри группы действует цель. Length сохраняет
прежний порядок. Полная длина для ранжирования вычисляется тем же интегралом
отводов, что и для принятого кандидата, с кэшем по форме отвода.

Если меняешь цель, проверь сразу `shortlist`, `order`, `improves`, `batch`,
`refine`, ветку single-coil и резервные N. Одной сортировки таблицы недостаточно.
Название «минимум» означает минимум среди действительно проверенных и
принятых вариантов, а не доказанный глобальный оптимум.

## Таблица, выбор и ручная проработка

### Данные решателя и Worker

- `calculations`: компактная скалярная запись каждого реального Teplo-вызова.
  Внутри могут быть accepted/rejected/error/outside, но интерфейс показывает
  **только accepted**. Удалённые владельцем колонки статуса, ΔQ, примечания и
  выходных температур не возвращать без запроса.
- `acceptedDesigns`: полные принятые конструкции с геометрией и исходной поверкой.
  Worker сохраняет их приватно и удаляет этот массив перед postMessage.
- `rows[balanced]`: рекомендация по выбранной цели, не все варианты таблицы.
- `selectedCalculationId`: номер автоматической рекомендации в текущем поиске.
- `geometryKey`: физическая идентичность аппарата. Не включает видимость.

Протокол Worker:

```text
Запуск: {id, state} → balance / progress / variants
Отмена: {id, cancel:true}
Выбор:  {id, selectCalculation:true, calculationId, selectionRequest}
Ответ:  selected + один design, либо selection-error
```

Выбор использует приватный кэш, без нового подбора и Teplo в проектном Worker.
Обычная поверка геометрии редактора в своём Worker может обновляться отдельно.
Кэш привязан к текущему id; устаревший/отменённый запрос выбирать не может.

### Загрузка выбранной строки

`selectCalculatedConstruction` → Worker → `applyCalculatedConstruction` →
`loadCoilVariant` → `verificationState` → поля, чертежи, 3D, поверка.

В `currentVariants.rows` добавляется выбранный профиль `calculation-N`.
Это пользовательский выбор из таблицы, а не новая целевая функция.
Сортировка только переставляет строки и не выбирает другую конструкцию.
Radio и подсветка показывают выбранную исходную конструкцию. Повторное нажатие
на выбранный radio загружает её исходную геометрию заново; последующие ручные
правки заменяются именно этим явным действием пользователя.

### Что сохраняется в листе

| Поле | Содержимое |
|---|---|
| verification-state | Текущая геометрия редактора, в том числе ручные правки |
| coil-variant-binding | key/profile/manual, userSelected/calculationId/geometryKey |
| selected-variant | balanced или calculation-N |
| coil-thermal-inputs | Настройки поверки, в том числе arrangement |

`coilProjectKey` учитывает activeId листа, исходные потоки, геометрию,
флаги и цель. Ответы проверяются по id запроса, выбор — дополнительно по
selectionRequest. При восстановлении после перезагрузки вариант сопоставляется
по geometryKey: номера вызовов могут измениться после изменения алгоритма.

Восстановление метаданных не перезаписывает сохранённую геометрию редактора.
При изменении задания ранее выбранная пользователем конструкция сохраняется
как ручная. Если исходной конструкции больше нет среди подходящих, radio в
новой таблице не отмечен. Не выбирай автоматически «похожую» строку по номеру.

Не вкладывай binding, verification-state, coil-thermal-inputs или вложенный
verification-design внутрь `verification-design.inputs`: это создаёт
рекурсивные снимки и раздувает localStorage. Данные localhost и github.io
раздельные; публикация не переносит пользовательские листы.

## Как безопасно изменить конкретное правило

| Запрос владельца | Основные места | Проверки |

выбора и ручных правок. Обнови страницу после изменения статических файлов.

## Публикация

Без явной команды владельца изменения остаются локальными. После команды
публикации: проверки → коммит в `codex/development` → синхронизация рабочей
ветки → чистый каталог → обновление main без потери чужих коммитов → push main
→ успешный GitHub Pages deployment → проверка публичных файлов → возврат в
`codex/development`. Не используй force push или reset --hard для расхождений.

Публичный сайт: https://oslablyat.github.io/PhysNowHEX/ . Pages публикует main,
корень репозитория. Следуй подробным правилам корневого AGENTS.md.
